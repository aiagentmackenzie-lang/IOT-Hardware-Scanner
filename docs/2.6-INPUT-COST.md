# 2.6.0 — input cost is bounded, and the evidence is real

Status: **implemented**. No input format, report schema (6), profile version
(5.0) or exit code changed. A control's evidence rule and two cost bounds did.

This slice came out of the P2 performance contract. The contract measured a
cold tree scan at **17.287 s / 470.8 MiB** on a 98.6 MiB fixture — a 4.8×
memory ratio that nobody could explain. Diagnosing it (P2 §3.2) found the cause,
and a worse problem in the same ten lines of code: **the scanner could report a
verification step that was never there.**

---

## 1. What was wrong

### 1.1 A control selected files by their path, then decoded them as text

Control 5 ("secure firmware update mechanism") picked candidates with a path
substring test — `update`, `upgrade`, `firmware`, `ota`, `sysupgrade` — and then
read each one through `_read_text_bounded`, which decoded up to
`max_scan_file_size_mb` (**50 MiB**) as **UTF-8 with `errors="replace"`**.

A directory named `usr/share/firmware/` therefore selected 24 binary blobs.
Arbitrary bytes decode to code points above U+FFFF, so the result is a
**4-byte-per-character** string: a 50 MiB file can become a ~200 MiB string, and
`.lower()` made a second one. On CPython 3.12.14/macOS the discarded strings were
not returned (measured: **+15.3 MiB of RSS per 4 MiB file, linear, after
`gc.collect()`**; flat for UCS-1/UCS-2 strings, flat for direct allocation, same
under `PYTHONMALLOC=malloc`).

Attribution, on the same fixture:

| Scan | Peak RSS |
| --- | --- |
| as shipped | **470 MiB** |
| control 5's read decoded as `latin-1` | 97 MiB |
| control 5's read removed | 89 MiB |

A hostile rootfs of 50 MiB blobs named `firmware-*` is a memory-amplification
denial of service. The 2.5.0 hostile-input slice did not catch it because it
measured crashes and time, not resident cost.

### 1.2 The same control produced false evidence

On that fixture control 5 reported **`PERFORMED / REVIEW`** with the evidence
*"24 update-related file(s); a verification step is present in
tree/usr/share/firmware/blob-00.bin, …"*. The "verification step" was
`verify|signature|gpg|sha256sum|checksum|ed25519` found in **random binary
bytes**; 7 of the 24 blobs contain one of those strings by chance.

A binary blob is not an update script, and a coincidental byte sequence is not
evidence that the device verifies anything. This is the failure the control
rules exist to prevent ("no PASS without positive evidence"), reached through
file **selection** rather than through a scoring rule.

### 1.3 A per-domain scan made text facts quadratic

`c2_detector._text_facts_from_content` decided whether a domain appeared only
inside an email address with

```python
standalone = content.lower().count(domain)          # once per unique domain
```

so its cost was `domains × bytes`, both attacker-controlled: 1,028 domains over
4 MiB was 4.3 GB of scanning for one file, and a file with 20,000 unique domains
in 4 MiB took ~3 s.

## 2. What changed

### 2.1 Control 5: screen, stream, and name what was inspected

`scanner/risk_scorer.py`:

* A path keyword now only nominates a **candidate**. `_looks_textual()` reads the
  first 8 KiB and rejects a file with a NUL byte or more than 5 % non-printable
  bytes. A binary artifact named like an updater is never decoded as text.
* The keyword test streams **lines**, not a file: `iter_lines(budget=256 KiB,
  max_line=12 KiB, encoding="latin-1")`. Latin-1 is deliberate — the keywords are
  ASCII and decoding byte-to-char keeps the cost at one byte per character
  whatever the file holds. A line longer than the cap is yielded empty by the
  reader, so an unterminated line cannot become the whole budget.
* At most **50** text files are examined; the cap is reported.
* The evidence now names **the file, the line and the keyword**, and states how
  many paths were candidates, how many text files were inspected and how many
  binaries were skipped.
* Three verdicts, not two:
  * a text file with a verification step → `PERFORMED / REVIEW`;
  * text files inspected and none has one → `PERFORMED / FAIL`;
  * **no readable text file at all** → `INCONCLUSIVE / UNKNOWN`. A binary named
    `firmware.bin` is not evidence either way, so it cannot produce a FAIL that
    an operator would read as "the updater is unsigned".
* `_read_text_bounded` is gone from this module; nothing else used it.

### 2.2 Text facts: one pass, not one per domain

`scanner/c2_detector.py`:

* `Counter(_DOMAIN_RE.findall(content))` for domain-token totals and
  `Counter(email host)` for email occurrences; a domain is email-only when every
  occurrence is an email host. Cost is linear in bytes.
* Counting **tokens** also fixes a quieter defect: `foo.com` appearing only
  inside `foo.com.br` used to be counted as a standalone occurrence and cleared
  as a C2 candidate. `TEXT_FACTS_VERSION` moves 1 → 2 so cached facts from the
  old extractor are not reused, and `_is_email_domain_text` now uses the same
  pass instead of re-scanning the content once per domain.

### 2.3 The benchmark harness learned a lesson too

`benchmarks/cases.py` keyed the warm cache's "populated" marker on the fixture
plan alone. When `TEXT_FACTS_VERSION` moved, every text-facts entry missed and a
*warm* benchmark silently timed a half-cold run (5.36 s instead of 0.84 s). The
marker now records the engine version, the facts-extractor version and the
rule-set digest. `measure.py` also stopped preparing fixtures inside the child
that is being measured: compiled rules added ~16 MiB to every case's peak RSS.

## 4. Before and after (P2 fixtures, same machine)

| Case | 2.5.1 | 2.6.0 | |
| --- | --- | --- | --- |
| Cold tree scan | 17.287 s / **470.8 MiB** | **9.762 s / 73.5 MiB** | 1.8× faster, **6.4× less memory** |
| Warm tree scan | 1.813 s / 480.9 MiB | **0.843 s / 65.0 MiB** | 2.2× faster, 7.4× less memory |
| Device-tree parse | 11.057 ms / 45.1 MiB | 10.982 ms / 41.8 MiB | unchanged within noise |
| 2 GiB windowed entropy | 31.101 s / 76.2 MiB | 31.008 s / 68.8 MiB | unchanged within noise |

The cold scan also got faster, not only smaller: the 373 MiB of strings that no
longer exist were being allocated and touched. Baseline re-recorded with
`benchmarks/record_baseline.py`; the fingerprint's `engine` field is recorded but
not compared, precisely so a release does not expire its own baseline.

## 5. What this does **not** claim

* **A verification keyword in a script is still weak evidence.** It says the
  shipped script contains a signature check, not that the script runs, that the
  key is pinned, or that the device enforces it. Check 6 keeps that unknown, and
  the evidence text says so. The change is that the evidence now comes from a
  text file at a named line, not from random bytes.
* **The text screen is a heuristic.** A binary with no NUL bytes and ≥95 %
  printable bytes could pass it. It is a bound and a filter, not a proof of
  file type; the scan's own format detection is unchanged.
* **The 256 KiB / 50-file budget can miss a verification step** in an enormous or
  unusually late part of a script tree. The truncation is stated in the evidence
  rather than silent, and the alternative — reading everything — is the defect
  this slice removed.
* **Email-only detection is token-based now.** A domain that appears only as a
  substring of a longer token is no longer counted as a standalone occurrence.
  That is the intended correction, and it is a behaviour change, recorded in
  `TEXT_FACTS_VERSION`.
* **No memory ceiling is asserted for a whole scan.** The P2 baseline pins the
  measured value on a named machine; a hostile-corpus RSS ceiling would need a
  separate bounded-resources row (the 2 GiB entropy row covers the reader only).

## 6. Reproduce

```bash
# The defect, on the P2 fixture tree
python benchmarks/measure.py --case cold-scan        # peak RSS, one child per case

# The evidence rules
pytest tests/test_control_matrix.py -k control_5 -v
pytest tests/test_c2_detector.py -k "email or cost" -v
```
